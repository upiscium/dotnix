# /design-to-issues — Planning ワークフロー

対象: $ARGUMENTS

このセッションのモデルが Opus 5.5 でなければ、最初にその旨を User に伝える（Planning は Opus 5.5 のセッションで行う想定: `claude --model claude-opus-5-5`）。続行するかは User が決める。

## 原則
- 設計上の重要な採否は User が決める。承認されていない判断を暗黙の承認として扱わない。沈黙・曖昧な返答は承認ではない。
- Human Decision が必要になった時点で、その場で AskUserQuestion か通常の質問で提示する（最後にまとめて聞かない）。
- 実装はしない。この段階で変更してよいのは、ドラフトファイルと（承認後の）Issue のみ。

## 手順
1. **要求分析**: 要求を読み、目的・制約・非対象範囲・成功条件を特定する。コードベースの調査は `repository-researcher`（Haiku）に任せてよい。分からないことは推測で埋めず質問する。
2. **仕様整理**: 曖昧さを列挙し、決められるものは User に確認する。
3. **全体設計 → 詳細設計**: 構成・インターフェース・データの流れ・エラー時の振る舞い・テスト方針。重要な分岐は Human Decision にする。
4. **タスク分割**: Sonnet が追加の仕様推測なしに着手できる粒度に分け、依存関係（順序・並列可否）を整理する。1 Issue は 1 つのまとまった PR で完結する大きさにする。
5. **Issue 作成前の確認**: Issue 案の一覧（タイトル・目的・依存）と、設計上の重要な採否を User に提示し承認を得る。Issue の全文はチャットに貼らず、下書きファイルの場所と要点を示す。
6. **Issue 作成**: 承認後に `gh issue create` で起票する（承認された分のみ）。下書きは先にファイルへ書く。起票後、番号と依存関係を一覧で報告する。

## Human Decision の書き方
冒頭に次を置く。
- **決めること**（1 文）
- **選択肢ごとの結果**（選んだ場合に何が起きるか）
- **推奨案とその理由**
判断に必要な前提知識は短く補う。作業中に付けた略称は、判断に関わるなら内容で言い換える。テスト件数や変更行数を判断材料の中心にしない。

## 各 Issue の必須項目
- 背景と目的
- 実装すべき振る舞い
- 受入条件（検証可能な形で）
- 変更可能な範囲（ファイル・モジュール）
- 禁止事項・非対象範囲
- 依存関係（先行 Issue 番号）
- 検証方法（実行コマンド・確認手順）
- Human Decision が必要な事項（実装中に Sonnet が止まって確認すべき点。無ければ「無し」）
- エスカレーション先: 仕様矛盾・設計変更が必要なら実装を止めて Opus 設計セッションへ戻す旨

## 禁止
User の承認なしの Issue 起票・更新、Commit / Push / PR、実装コードの変更。
