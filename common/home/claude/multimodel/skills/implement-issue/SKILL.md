# /implement-issue — Execution ワークフロー

対象: $ARGUMENTS

## セッションごとの動き
- **Sonnet 5.5 のセッション（推奨: `claude --model claude-sonnet-5-5`）**: 自分が実装責任者として以下を実行する。
- **Opus のセッション（単一セッション運用）**: 自分では実装せず、Issue 本文を `issue-implementer` subagent に渡して丸ごと委譲し、その報告を User 向けに整理する。Opus のトークン消費が大きいため、日常運用は別セッション方式を推奨する。

## 手順
1. **Issue の確認**: `gh issue view <番号>`（読み取りのみ）などで取得し、背景・振る舞い・受入条件・変更可能範囲・禁止事項・依存関係・検証方法を確認する。依存 Issue が未完了なら着手せず User に伝える。仕様に不足・矛盾があれば実装前に報告する（推測で補わない）。
2. **既存実装の調査**: 広い検索や依存抽出は `repository-researcher`（Haiku）へ。小さければ自分で読む。
3. **計画の具体化**: 変更ファイル・テスト・順序を決める。変更可能範囲を超える場合は停止して報告する。
4. **実装とテスト**: 独立した部分実装・テスト・難しいデバッグは `implementation-helper` に、範囲と完了条件を明示して委譲してよい（任意。小さい作業は直接行う）。同時起動は最大 4。
5. **レビュー**: `code-reviewer`（同一モデル系列の独立コンテキストレビューであり、別プロバイダーの独立レビューではない）を実行し、指摘に対応する。
6. **受入条件の照合**: 受入条件ごとに、実際に実行した検証の結果と対応づける。実行していない検証を実行済みと書かない。
7. **報告**: 下記の形式で報告する。

## Opus へのエスカレーション
Issue 仕様の矛盾／受入条件を満たすと既存設計が破綻する／重要なインターフェース変更が必要／既存の設計判断を覆す必要がある／複数 Issue に影響する構造変更が必要／合理的な再試行が 2 回失敗し設計の問題が濃厚、のいずれか。
該当したら実装を止め、`architecture-reviewer`（Opus）に問題と根拠を渡して分析させ、その結果（問題・代替案・影響範囲）を User に提示して採否を求める。採否を自分や architecture-reviewer が決めない。単純なテスト失敗や局所的ミスはエスカレーション不要。

## 報告形式（Human Decision 報告）
冒頭に User が決めること（受け入れ可否・エスカレーション要否など）と選択肢ごとの結果。続いて:
- 当初の目的（1〜2 行）
- 実際の実装（何を・どこに・どう変えたか。振る舞いが変わる点）
- 目的とのずれ（足したもの・やらなかったもの・自分で解釈したもの。無ければ「無し」）
- 確認できていないこと
通過したテスト・レビューの件数や変更行数は書かない。失敗・未実施・未解決のレビュー指摘・受入条件未達は必ず書く。詳細は PR/Issue のリンクで示す。

## 禁止
仕様・目的・受入条件・変更許可範囲の独断変更。Commit / Push / PR / Issue 更新は Issue または User が許可した場合のみ。subagent の再帰的な再委譲（`issue-implementer` が `issue-implementer` を起動する等）。
